# Пульс маршрутов — frontend диспетчера

Vue 3 + Vite. Интерфейс для задачи прогноза отклонений наземного транспорта за 10–15 минут до плановой остановки. На стартовом экране выбирается исторический прогон через backend и ML либо живой NDTP-поток. Полная инструкция для трёх модулей — в [корневом README](../README.md).

## Запуск

```bash
cd frontend
npm ci
npm run dev
```

Откройте `http://localhost:5173`. Для статической сборки: `npm run build`, затем `npm run preview`.

Для всей системы используйте корневой `compose.yaml`. Отдельный образ frontend собирается так:

Из корня репозитория:

```bash
docker build -t metro-pulse-frontend ./frontend
docker run --rm -p 8080:80 metro-pulse-frontend
```

Отдельный контейнер требует доступного DNS-имени `backend` для `/api/*`; без backend интерфейс покажет ошибку соединения.

> Запросы идут на `/api/*` того же origin: Vite проксирует их в локальный backend, Nginx в Docker — в сервис `backend`. `VITE_API_BASE_URL` нужен лишь для отдельного origin.

## Что показано

- Крупный оперативный сигнал с прогнозом опоздания и временем до целевой остановки. Интерактивная карта Москвы с положением ТС по последнему GPS-пакету **не позже T**, цветом риска и целевой остановкой. Плановые остановки соединены упрощённой линией: она не является восстановленной дорожной трассой или map matching.
- Прогноз задержки в секундах и понятном округлении до минут, текущая задержка, время планового прибытия, плановый участок, наблюдаемый сигнал, возраст телеметрии и простое действие для диспетчера. Действие задаётся правилом интерфейса.
- Риски: `>120 с` — высокий, `60…120 с` — внимание, остальное — норма. Это правило UI, не вероятность ML.
- Историческое воспроизведение, список и поиск прогнозов, фильтр риска, экспорт текущего среза, светлая и тёмная темы.
- What-if: арифметическое снижение прогнозной задержки на выбранное число секунд. Это иллюстрация сценария, не результат повторного инференса.
- При недоступности API сохраняется последний полученный срез и видна ошибка связи.

В историческом режиме frontend запускает `/api/v1/replay/start` и читает `/api/v1/replay`: backend вычисляет 151 прогноз на `dataset/validate` через ML-сервис. `src/data/demo_fleet.json` даёт карте плавные GPS-треки. `src/data/demo.json` и `ml_service/research/vovchik/predictions_validate.json` остаются сохранёнными исследовательскими результатами и в этом режиме не загружаются. `npm run data:demo` может пересобрать эти файлы. Исторический CSV не является бинарным NDTP-пакетом.

По умолчанию карта улиц загружается браузером с `tile.openstreetmap.org` и требует сети. Для подложки Яндекс Карт создайте ключ **Tiles API** и вставьте его после `VITE_YANDEX_TILES_API_KEY=` в `frontend/.env`, затем перезапустите Vite или пересоберите frontend. Если ключ не должен попадать в Git, задайте его вместо этого в игнорируемом `frontend/.env.local`. Можно выбрать `VITE_YANDEX_MAP_STYLE=map|future_map|driving|transit|admin`; без ключа остаётся OpenStreetMap. Запрашивается `projection=web_mercator`, соответствующая Leaflet, чтобы позиции и линии не смещались. Официальный логотип Яндекса, ссылка «Открыть в Яндекс Картах» и атрибуция включаются автоматически. Если тайлы Яндекса не загрузились, карта переключится на OSM. Ключ попадает в браузерные запросы по устройству Tiles API, поэтому ограничьте его в кабинете Яндекса по домену. Перед использованием для реальной диспетчеризации проверьте условия лицензии Яндекса: общий пункт 5.1.3 ограничивает мониторинг транспорта, а пункт 6.5.1 отдельно допускает использование Tiles API с собственными данными в закрытых системах.

Для своей резервной картографической инфраструктуры можно задать `VITE_MAP_TILE_URL` и `VITE_MAP_ATTRIBUTION`; сервер OSM не следует использовать для массовой загрузки или офлайн-кэша. При недоступности обеих подложек позиции и линии остаются видны на однотонном фоне.

## Подключение backend

Адаптер находится в `src/services/dataSource.js`; в живом режиме он раз в 5 секунд запрашивает `GET /api/dashboard`, `/api/v1/fleet` и `/api/v1/ndtp/status`. Исторический режим опрашивает `/api/v1/replay`. Для запуска всей системы используйте корневой `compose.yaml`.

Минимальный ответ:

```json
{
  "date": "2026-01-06",
  "records": [{
    "sampleId": "134040_1767733200",
    "vehicleId": "134040",
    "timestamp": "2026-01-06 21:00:00",
    "targetTime": "2026-01-06 21:11:00",
    "targetStopId": "...",
    "targetAddress": "ул. 26-ти Бакинских Комиссаров, д.3А",
    "segmentLabel": "ул. Покрышкина, д.7, к.1 → ул. 26-ти Бакинских Комиссаров, д.3А",
    "position": [37.5, 55.7],
    "targetCoordinate": [37.51, 55.71],
    "telemetryTime": "2026-01-06 20:59:53",
    "telemetryAgeSec": 7,
    "speedKmh": 17,
    "meanSpeedKmh": 12,
    "stopFraction": 0.2,
    "currentDeviationSec": 253,
    "predictionSec": 264,
    "horizonSec": 660,
    "signal": "Уже есть отклонение",
    "route": [[37.50,55.70],[37.51,55.71]],
    "trail": [[37.49,55.7],[37.5,55.7]]
  }]
}
```

Координаты в порядке `[долгота, широта]`; время — МСК в формате `YYYY-MM-DD HH:mm:ss`. `records` содержит последние и исторические прогнозные точки, из которых экран выбирает актуальные на момент просмотра. Важно выдавать прогноз, сформированный на `T`, только из данных `event_time ≤ T`; `targetTime - T` должно быть в окне `(10, 15]` минут. Для live режима backend должен также передавать состояние потока, подтверждённые latency и причины, если они будут реализованы. До этого UI не показывает фиктивные вероятности, MAE или throughput.

## Основание интерфейса

Основные критерии взяты из ТЗ хакатона: ранний алерт, понятность за несколько секунд, карта ТС и уровня риска, карточка инцидента, работа при обрыве связи. Демо опирается на формат CSV из исходного README и на NDTP спецификацию для понимания полей телеметрии. Backend предоставляет OpenAPI и работает вместе с ML и frontend в Compose; TCP-приёмник NDTP и инструкция его запуска описаны в корневом README.
