# Metrohack: живой NDTP, бэк и фронт

[Краткая инструкция для жюри](JURY_GUIDE.md): запуск, два источника данных, прогнозы, алерты и метрики.

## Структура проекта

| Папка | Что внутри |
|---|---|
| `backend/` | TCP-приём NDTP, исторический прогон, REST API, тесты и конфигурация устройств |
| `frontend/` | Vue-дашборд, карта и подготовленный GPS-трек для плавного воспроизведения |
| `ml_service/app/` | Сервис инференса и модели, которые попадают в Docker-образ |
| `ml_service/research/vovchik/` | Основной notebook обучения задержки и риска, скрипт запуска, тесты и результаты |
| `ml_service/research/mishgan/` | Исследовательский notebook с альтернативными признаками |
| `dataset/` | Train/test/validate, исходные CSV и `dataset/submission.csv` |

Из корня репозитория модели можно переобучить командами `pip install -r ml_service/research/requirements.txt` и `python ml_service/research/vovchik/train_from_notebook.py`. Скрипт последовательно исполняет ячейки основного notebook. Полученные модели лежат в `ml_service/research/vovchik/results/`; Docker использует проверенные копии в `ml_service/app/artifacts/`. Подробности и метрики — в [документе об ML](ml_service/research/vovchik/ML_RISK.md).

Запуск приложения из этой папки с эмулятором организаторов:

```powershell
docker load -i .\ndtp-telemetry-emulator.tar  # один раз, если образ ещё не загружен
docker compose up --build -d
```

Файл `ndtp-telemetry-emulator.tar` нужно получить отдельно и положить в корень репозитория: он не входит в Git из-за размера. Если его нет, весь исторический режим и TCP-приёмник NDTP запускаются без локального генератора пакетов: `docker compose -f compose.history.yaml up --build -d`. Для живой телеметрии в этом варианте подключите внешний источник к порту `9201`.

- Фронт: http://localhost:8080
- Бэк: http://localhost:8000/docs
- NDTP TCP: порт `9201` хоста (не HTTP).
- `GET /api/v1/ndtp/status` — соединения, пакеты, ошибки и известные соответствия ID.
- `GET /api/v1/fleet` — последние GPS-позиции **всех** ТС, от которых поступила телеметрия за 15 минут, включая ТС без прогноза.
- `GET /api/dashboard` — только созданные ML-прогнозы. Пустой поток возвращает пустой массив, а не историческое демо.
- `POST /api/v1/replay/start` и `GET /api/v1/replay` — отдельный исторический прогон validate через backend и ML.

При открытии фронта выберите источник: **«Тестовые данные»** запускает исторический прогон через backend и ML, **«Эмулятор NDTP»** подключает живые `/api/dashboard`, `/api/v1/fleet` и `/api/v1/ndtp/status`. Источник можно сменить в верхней панели. В историческом режиме воспроизведение начинается автоматически на скорости `×0,25`; селектор над картой позволяет выбрать `×0,25`…`×4`. Тема карты следует теме интерфейса; при первом открытии интерфейс учитывает тему браузера/системы.

Тестовый режим берёт 151 прогнозную точку из `dataset/validate/points.csv`, историческую телеметрию из `traffic.csv` и план из `schedule_plan.csv`. Backend отдельно от живого NDTP-потока собирает признаки на время `T` и вызывает ML-сервис для каждой точки; `cur_dev_s` берётся из `points.csv`, ответы validate и готовые предикты не читаются. GPS-треки для плавной карты загружаются из подготовленного `frontend/src/data/demo_fleet.json`. Исторический CSV проходит через backend, но не притворяется бинарным NDTP-пакетом. Сохранённый `predictions_validate.json` остаётся исследовательским артефактом и не подаётся во frontend в этом режиме.

Под картой есть компактная панель телеметрии выбранного ТС. В «Динамике» показаны сводка по всем видимым ТС, сумма **положительных** прогнозируемых отклонений по ТС с актуальным прогнозом и таблица транспорта. В таблице GPS указана последняя реально полученная точка со временем её фиксации и приёма; интерполированная позиция служит только для анимации карты. Прогноз показан числом секунд, а рядом указана вероятность задержки больше двух минут. В NDTP-пакете нет ID маршрута, поэтому без подтверждённой связи `unitId → tr_id → маршрут` группировка именно по маршрутам невозможна.

`docker compose up` поднимает **тестовый NDTP-эмулятор** с четырьмя устройствами `9900001`, `9900101`, `9900201`, `9900301`. Эти ID не пересекаются с известными устройствами датасета. Бэк конфигурирует его автоматически и повторяет настройку после перезапуска эмулятора. На фронте эти маркеры подписаны как «эмулятор». Конфигурация устройств находится в `backend/config/ndtp_emulator.json`; Dockerfile бэка копирует её в контейнер. Для реального потока терминалы подключаются к тому же TCP-порту `9201`. Автогенерация эмулятора выбирает случайный курс и **не следует дорогам**; её координаты показываются как получены, без выдуманной привязки к улице.

Для каждого нового NDTP `unitId` бэк автоматически создаёт ТС с `vehicleId = unitId`. Из `dataset/train/traffic.csv` извлечены 56 однозначных соответствий `unit_id → tr_id`; они записаны в `backend/config/ndtp_units.csv` и загружаются при старте. Для другого устройства можно добавить соответствие через `POST /api/v1/ndtp/units`.

Если организаторы передают актуальный `traffic.csv`, укажите внутри контейнера `NDTP_TRAFFIC_PATH` и примонтируйте файл. Бэк прочитает поля `unit_id`, `tr_id`, `event_time` и сопоставит устройство с `tr_id` **на дату пакета**. Это важно, когда одно устройство используется в разные дни на разных рейсах. Неоднозначные соответствия в пределах дня остаются без прогноза, но телеметрия видна под `unitId`; точное соответствие можно задать через `POST /api/v1/ndtp/units`. Например, добавьте в локальный Compose override:

```yaml
services:
  backend:
    environment:
      NDTP_TRAFFIC_PATH: /app/traffic.csv
      SCHEDULE_PLAN_PATH: /app/schedule_plan.csv
    volumes:
      - ./organizer/traffic.csv:/app/traffic.csv:ro
      - ./organizer/schedule_plan.csv:/app/schedule_plan.csv:ro
```

В NDTP-пакете нет ID остановки или маршрута: `unitId` соответствует `unit_id` из `traffic.csv`, а `tr_id` связывает телеметрию с `schedule_plan.csv`. Согласно сообщению организаторов в экспортированном чате от 25.09.2026, ТС без плана остановок могут встречаться в потоке и не требуют прогноза. Поэтому для новых дат нужно предоставить актуальный план остановок; сопоставление ID само по себе его не заменяет.

Карта показывает все ТС с валидным GPS. Если пакет давно не приходил, маркер становится серым; ТС без валидного GPS перечисляется в счётчике, но не имеет точки на карте. Карта обновляется каждые 5 секунд и рисует полученный GPS-трек, без искусственного перемещения маркеров. При обновлении позиции ручной масштаб карты сохраняется; кнопка «Показать весь транспорт» снова подгоняет вид под все ТС.

## Условия прогноза

Для ML-прогноза дополнительно нужны:

1. Актуальное расписание с `tr_id`, временем и координатами остановок. Его можно подать через `POST /api/v1/schedule` или заменить CSV, на который указывает `SCHEDULE_PLAN_PATH` внутри контейнера.
2. Измеренное текущее отклонение от графика — через `POST /api/v1/arrivals` или оценку по GPS при распознанном прибытии на остановку. `POST /api/v1/current-deviation` позволяет задать известное значение вручную.
3. Остановка в окне `(сейчас + 10 мин, сейчас + 15 мин]`.

В комплекте есть план остановок только за **6–7 января 2026 года**. Он годится для исторических проверок, но не даёт прогнозов для текущего живого потока. Отсутствие прогноза не скрывает ТС с карты; при выборе его маркера интерфейс показывает причину.
