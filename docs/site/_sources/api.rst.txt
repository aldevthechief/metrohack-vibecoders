HTTP API и Swagger
==================

Спецификации экспортированы через ``app.openapi()`` из настоящих приложений.
Типы, обязательность полей и стандартные ответы в JSON соответствуют коду.
Для маршрутов с ответом ``dict`` схема не перечисляет все динамические поля;
для них смотрите пояснения и реализацию в справочнике.

Статические страницы Swagger ниже работают в режиме чтения. Для выполнения
запросов используйте ``/docs`` запущенного сервиса на своей машине.

Transport Delay Predictor Backend
---------------------------------

* `Статический Swagger backend <backend-swagger.html>`_.
* :download:`OpenAPI JSON <openapi/backend.json>`.
* Swagger работающего сервиса: http://localhost:8000/docs.

GET /health
~~~~~~~~~~~

Проверка ответа процесса Backend. Возвращает status=ok; состояние ML и свежесть телеметрии этим запросом не проверяются.

POST /api/v1/telemetry
~~~~~~~~~~~~~~~~~~~~~~

Принимает один нормализованный JSON-пакет и запускает общую цепочку обработки. Ответ prediction_updated показывает, удалось ли сформировать новый прогноз. Бинарный NDTP принимается отдельно по TCP 9201.

Тело: JSON, модель ``TelemetryPoint``.

POST /api/v1/ndtp/units
~~~~~~~~~~~~~~~~~~~~~~~

Регистрирует ручное соответствие устройства unit_id рейсу tr_id. Меняет состояние; ручная привязка имеет приоритет перед CSV.

Тело: JSON, модель ``NdtpUnitMapping``.

GET /api/v1/ndtp/status
~~~~~~~~~~~~~~~~~~~~~~~

Состояние TCP-приёмника: listening, число клиентов и принятых пакетов, обновления прогнозов, отклонённые кадры, ошибки обработки и сопоставления устройств.

POST /api/v1/replay/start
~~~~~~~~~~~~~~~~~~~~~~~~~

Запускает исторический прогон, если он ещё не запускался или завершился ошибкой. Возвращает текущее состояние; расчёт продолжается в фоне. Повторный запрос при running или complete не запускает второй прогон.

GET /api/v1/replay
~~~~~~~~~~~~~~~~~~

Состояние исторического прогона: idle/running/complete/failed, completed, total, error, records и timelineTimestamps. Исторические результаты отделены от живого потока.

GET /api/v1/vehicles
~~~~~~~~~~~~~~~~~~~~

Список идентификаторов рейсов, присутствующих в хранилище телеметрии.

GET /api/v1/fleet
~~~~~~~~~~~~~~~~~

Текущий парк с положением, скоростью, курсом, статистикой за 5–15 минут и predictionStatus. Включает транспорт без доступного прогноза.

GET /api/v1/vehicles/{tr_id}/latest
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Последний доступный пакет рейса. Если пакета нет, возвращает 404.

Параметры:

* ``tr_id`` (path, обязательный).

GET /api/v1/vehicles/{tr_id}/history
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Сохранённая история рейса в памяти; для неизвестного рейса список пуст. Окно хранения по умолчанию — 15 минут.

Параметры:

* ``tr_id`` (path, обязательный).

POST /api/v1/schedule
~~~~~~~~~~~~~~~~~~~~~

Добавляет или обновляет плановую остановку рейса. Для дальнейшего прогноза цель должна иметь координаты и согласованное плановое время.

Тело: JSON, модель ``SchedulePoint``.

GET /api/v1/schedule/{tr_id}
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Возвращает плановые остановки указанного рейса.

Параметры:

* ``tr_id`` (path, обязательный).

POST /api/v1/current-deviation
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Задаёт текущее отклонение рейса в секундах с источником provided. Положительное значение означает опоздание.

Тело: JSON, модель ``CurrentDeviation``.

POST /api/v1/arrivals
~~~~~~~~~~~~~~~~~~~~~

Принимает фактическое прибытие, находит остановку в плане и сохраняет отклонение actual_time минус time_begin с источником arrival-feed. Если остановки нет, возвращает 404.

Тело: JSON, модель ``ObservedArrival``.

POST /api/v1/prediction-context
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Сохраняет контекст и текущее отклонение после проверки существования целевой остановки. Не выполняет инференс сам по себе.

Тело: JSON, модель ``PredictionContext``.

GET /api/v1/vehicles/{tr_id}/features
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Рассчитывает телематические признаки рейса на ISO-момент at по пакетам, доступным к этому времени. Скорости — км/ч, интервалы — секунды.

Параметры:

* ``tr_id`` (path, обязательный).
* ``at`` (query, обязательный).

POST /api/v1/features/schedule
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Рассчитывает календарные и плановые признаки заданного контекста.

Тело: JSON, модель ``PredictionContext``.

GET /api/v1/vehicles/{tr_id}/spatial-features
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Рассчитывает расстояние и приближение к заданным координатам цели на момент at.

Параметры:

* ``tr_id`` (path, обязательный).
* ``at`` (query, обязательный).
* ``target_longitude`` (query, обязательный).
* ``target_latitude`` (query, обязательный).

POST /api/v1/features
~~~~~~~~~~~~~~~~~~~~~

Возвращает объединённые признаки для ML. Проверяет совпадение цели с расписанием, координаты и окно (10, 15] минут; некорректные условия дают 400.

Тело: JSON, модель ``PredictionContext``.

POST /api/v1/predict
~~~~~~~~~~~~~~~~~~~~

Собирает признаки и вызывает ML, возвращая прогноз и риск. Этот маршрут не записывает инцидент в дашборд. Ошибка контекста даёт 400, HTTP-ошибка ML — 503.

Тело: JSON, модель ``PredictionContext``.

POST /api/v1/incidents/evaluate
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Вычисляет прогноз и сохраняет последний инцидент рейса в IncidentService. В отличие от потоковой обработки, этот маршрут не вызывает запись в DashboardService. Ошибка контекста — 400, HTTP-ошибка ML — 503.

Тело: JSON, модель ``PredictionContext``.

GET /api/v1/incidents
~~~~~~~~~~~~~~~~~~~~~

Список последних сохранённых инцидентов по рейсам.

GET /api/v1/incidents/{tr_id}
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Последний инцидент конкретного рейса; если его нет, 404.

Параметры:

* ``tr_id`` (path, обязательный).

GET /api/dashboard
~~~~~~~~~~~~~~~~~~

Срез прогнозных записей DashboardResponse для интерфейса: позиции, маршрут, цель, задержка, вероятность и объяснения. Для ТС без прогнозов используйте отдельный fleet endpoint.

Transport Delay Predictor ML Service
------------------------------------

* `Статический Swagger ml <ml-swagger.html>`_.
* :download:`OpenAPI JSON <openapi/ml.json>`.
* Swagger работающего сервиса: http://localhost:8001/docs.

GET /health
~~~~~~~~~~~

Проверка ответа процесса ML после импорта приложения и загрузки моделей. Возвращает status=ok.

POST /predict
~~~~~~~~~~~~~

Принимает словарь features, нормализует его под фиксированную схему и вычисляет прогноз. predicted_delay_s — секунды задержки, delay_probability — вероятность события > 120 с, reason_factors — SHAP-вклады регрессора. Для осмысленного прогноза передавайте признаки, собранные Backend, а не произвольный пустой словарь.

Тело: JSON, модель ``PredictionRequest``.

Примеры и ответы
----------------

Без изменения состояния можно вызвать:

.. code-block:: bash

   curl http://localhost:8000/health
   curl http://localhost:8000/api/v1/ndtp/status
   curl http://localhost:8000/api/v1/fleet

Пример ручного отклонения (меняет состояние демонстрационного рейса):

.. code-block:: text

   POST /api/v1/current-deviation
   Content-Type: application/json

   {"tr_id": "demo-trip", "cur_dev_s": 90}

Этот запрос сам по себе не создаёт прогноз: нужны расписание и телеметрия.

* ``422`` — ошибка проверки входных полей FastAPI/Pydantic.
* ``400`` — некорректный контекст, горизонт или другие явно проверяемые данные
  на маршрутах, обрабатывающих ``ValueError``.
* ``404`` — запрошенное ТС, инцидент или плановая остановка не найдены.
* ``503`` — HTTP-вызов ML завершился ошибкой на маршрутах, которые её перехватывают.

Не все явно выбрасываемые ошибки перечислены в автоматической OpenAPI-схеме.
``GET /health`` подтверждает ответ процесса, но не свежесть NDTP и не качество ML.
