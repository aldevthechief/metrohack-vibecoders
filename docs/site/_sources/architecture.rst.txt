Архитектура и модули
========================

Путь данных
---------------

.. code-block:: text

   NDTP TCP :9201 ──> Backend ──HTTP──> ML :8001
                       │                │
                       │<── прогноз ────┘
                       │
                       └── REST API ──> Vue-дашборд :8080

Backend
-----------

``backend/app/main.py`` связывает сервисы и объявляет HTTP API.
При старте загружаются план и настройки устройств, запускается NDTP TCP-приёмник;
при наличии адреса эмулятора отдельная задача поддерживает его конфигурацию.

``NdtpServer`` проверяет заголовок и CRC бинарного кадра, handshake NDTP 6.2,
разбирает навигационную ячейку и определяет ``tr_id`` по ``unit_id``.
Ручное сопоставление имеет приоритет; сопоставление из traffic учитывает дату.
При неоднозначности рейс не угадывается.

``ProcessingService`` сохраняет телеметрию, проверяет прибытие на остановку,
выбирает следующую плановую цель и получает текущее отклонение.
При отсутствии цели или отклонения пакет остаётся доступен для отображения,
но новый прогноз не создаётся.

``FeatureService`` объединяет календарные, пространственные и телематические
признаки. Проверяет совпадение времени цели с зарегистрированным расписанием,
наличие координат и горизонт ``600 < horizon_s <= 900``.

``PredictionService`` отправляет признаки в ML с тайм-аутом 5 секунд.
``IncidentService`` формирует риск и наблюдаемый сигнал;
``DashboardService`` готовит записи для интерфейса.
``FleetService`` независимо показывает ТС с полученной телеметрией,
включая те, для которых прогноз ещё недоступен.

``VehicleStateService`` хранит историю в памяти, по умолчанию за 15 минут.
При выборке на момент T учитываются только пакеты, у которых одновременно
``event_time <= T`` и ``receive_time <= T``.
История и накопленные инциденты не являются постоянной базой данных:
перезапуск процесса сбрасывает состояние в памяти.

Исторический режим
----------------------

``HistoricalReplayService`` читает points и traffic, использует общий план
остановок, но отдельную историю ТС. Он собирает признаки и вызывает реальный
ML-сервис для каждой точки. Эталонные ответы validate и сохранённые прогнозы
для вычисления не читаются. Исторические пакеты не подменяют живой NDTP-парк.

ML
------

``ml_service/app/main.py`` предоставляет ``POST /predict``.
``ModelService`` при импорте приложения загружает артефакты из ``app/artifacts``.
Входной словарь приводится к фиксированному порядку 78 признаков.
Регрессор CatBoost предсказывает поправку к текущему отклонению;
результат возвращается в секундах задержки.

Отдельный классификатор оценивает вероятность события «задержка > 120 секунд».
``ml_risk.py`` содержит расчёт риска, калибровку, SHAP-вклады и проверки артефактов.
SHAP объясняет вклад признаков в регрессию, а не доказывает причину задержки.
Методика обучения и ограничения оценки находятся в
:download:`ML_RISK.md <../ml_service/research/vovchik/ML_RISK.md>`.

Frontend
------------

Vue 3 и Vite; в Docker статические файлы обслуживает Nginx.
``frontend/src/services/dataSource.js`` получает данные по REST API,
``App.vue`` управляет экранами, ``TransportMap.vue`` отображает карту Leaflet.
Nginx проксирует ``/api/*`` в Backend. Swagger на ``/docs`` открывается
непосредственно на порту сервиса, а не по адресу дашборда.

Линия маршрута соединяет плановые остановки и не является полноценным
map matching. При потере HTTP-соединения фронтенд сохраняет последний срез
и показывает ошибку связи.
